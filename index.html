1. The first principle of a DBMS: tables that point at each other

A database is not a pile of data. It is a set of tables, and every table has exactly one job: to describe one kind of thing. A STUDENT table describes students. A COURSE table describes courses. Each row is one thing. Each column is one fact about it.

Two rules make the whole system work, and every join you will ever write comes from them:

Rule 1 — Every row has a Primary Key (PK). One column whose value is unique and never NULL. It is the row's identity card: student_id, doc_id, course_id.

Rule 2 — A Foreign Key (FK) is one table storing another table's Primary Key. It is how tables "point" at each other. COURSE.student_id stores a value that must exist in STUDENT.student_id.

The arrow from FK to PK is your ON clause: ON course.student_id = student.student_id

Analogy: the class register and the library register

Your class register lists you once, with your roll number. When you borrow a book, the library register does not copy your name, department and phone number; it writes just your roll number. To find out who borrowed the book, the librarian follows the roll number back to the class register. The roll number in the class register is the primary key. The roll number copied into the library register is a foreign key. The librarian's "following it back" is a JOIN.

The one idea behind every join

A JOIN is just following an arrow. If you can find which column in table A equals which column in table B, you can write the join. If there is no arrow between two tables, you go through a third table that has arrows to both. That is all a "3-table join" is.

Why is data split into tables at all?

So that a fact is stored once. The department name "Cardiology" lives in one row of DEPARTMENT, not repeated on every doctor. That is what normalization means in one breath: store each fact once, in the table it belongs to, and use keys to connect. Joins put the facts back together at query time. Store once, join when needed.

2. The first principle of a query: you translate, you don't invent

A nervous student thinks a query has to be created. It doesn't. A SELECT is a sentence in a fixed grammar, and every application question is really asking the same thing:

Every question, decoded

"Show me WHAT, FROM which tables, for WHICH rows, grouped HOW, sorted HOW."
Your job is translation, not creativity. The English is already the query; you just move the words into the right slots.

The kitchen pipeline: the order Oracle thinks

You type SELECT first, but Oracle runs FROM first. This one fact explains almost every error you will ever see. Think of cooking:

  1. 1
    FROM + JOIN … ON — take ingredients out of the fridgeWhich tables? Connect them by following the key arrows.
  2. 2
    WHERE — wash and throw away bad rowsFilters individual rows. It runs before any grouping, so it cannot see totals.
  3. 3
    GROUP BY — arrange into platesOne plate per department, per doctor, per city. Every "each / per / -wise" in the question lands here.
  4. 4
    HAVING — throw away plates that fail a testFilters groups. The only place a condition on COUNT / SUM / AVG can live.
  5. 5
    SELECT — decide what goes on the serving trayColumns, aggregates, and clear aliases. Written first, decided last.
  6. 6
    ORDER BY — serve in orderRuns last, so it can use the aliases you gave in SELECT.

GROUP BY, drawn

GROUP BY does not delete rows. It sorts them onto plates and then hands you one row per plate. Six doctor rows become four department plates:

COUNT(*) counts what is on each plate, and the output has exactly one row per plate. That is why every plain column you SELECT must be a plate label, which means it must be in GROUP BY.

WHERE versus HAVING: the bouncer and the judge

WHERE is the bouncerStands at the door and checks one row at a time: "Status Completed? Come in." He has never seen a total in his life, so he cannot check "at least two".
GROUP BY is the seatingEveryone who got in sits at their doctor's table. One table per doctor.
HAVING is the judgeWalks table to table after everyone is seated: "Fewer than two at this table? Cleared away." Only the judge can see a table's total.
Two rules that fall out of this order

WHERE runs before GROUP BY, so it can't see totals. A condition on a total goes in HAVING.

SELECT runs after GROUP BY, so any plain column you SELECT must also be in GROUP BY (otherwise Oracle says ORA-00937 not a single-group group function).

Confidence trick: when you feel stuck, stop trying to write SELECT. Write FROM first. Once the tables and arrows are on the page, the SELECT writes itself at the end.

3. The six-move method (on paper, before you touch the keyboard)

Move 1 — Underline the nouns and the signal words

Nouns become tables and columns. Signal words tell you which clause to use. Read every question with a highlighter. This is Question 2 from the practice arena, marked the way you should mark it on paper:

"For every department, show the department name and the number of doctors working in it. A department that currently has no doctors must still appear in the list, showing 0. Show the departments with the most doctors first."

each / every → GROUP BY number of / total → COUNT / SUM even if none → LEFT JOIN first / arrange → ORDER BY only rows where → WHERE only groups with → HAVING treat NULL as → NVL

Four highlights, four clauses, and the query is already half-written in your head: FROM department LEFT JOIN doctor … GROUP BY dept_name … ORDER BY count DESC. The nouns give you the tables; the highlights give you the clauses.

Move 2 — Draw boxes and arrows

A five-second sketch: one box per table, one arrow per FK→PK link. Each arrow becomes an ON. Start from the table the question is about (the subject). "For each doctor…" means DOCTOR is the subject; "For every department…" means DEPARTMENT is.

Move 3 — Pick the join type with one question

Ask yourself

"Must a row appear even if it has no match in the other table?"
No → INNER JOIN (just write JOIN).
Yes → LEFT JOIN, with the table that must keep all its rows on the left.

Move 4 — Fill the skeleton in thinking order

Think FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Then write it in SQL order. The skeleton never changes:

SELECT <columns / aggregates> AS <alias>
FROM <subject table> s
JOIN <other table> o ON s.key = o.key
WHERE <row condition>
GROUP BY <every plain column in SELECT>
HAVING <condition on an aggregate>
ORDER BY <column or alias> DESC;

Leave out the lines the question doesn't need. A two-table lookup uses four lines; a full report uses all seven.

Move 5 — Alias everything

Short table aliases (d, dp, a) and readable column aliases (AS total_fee). The marking rubric literally awards marks for "clear aliases, easy to read", and prefixing every column with its alias kills the ORA-00918 column ambiguously defined error before it happens.

Move 6 — Predict the row count, then run

Before you press Enter, say the expected number of rows out loud. "Five departments, LEFT JOIN from DEPARTMENT, so at least five rows." If the output surprises you, that is information, not failure: it usually means the join type or the COUNT is wrong (see next page).

Analogy: the school dance

Departments line up on the left, doctors on the right, and a pair forms whenever the dept_id matches. INNER JOIN keeps only the pairs. LEFT JOIN keeps every department, even one standing alone; its partner's chair stays empty, and an empty chair is exactly what NULL looks like in the output. RIGHT JOIN keeps every doctor instead. Row-count sanity rule

INNER ≤ LEFT / RIGHT ≤ FULL. A LEFT JOIN never has fewer rows than the left table. If your "all departments" query shows 4 departments when the table has 5, you wrote an INNER JOIN.

The COUNT trap after a LEFT JOIN

Look at the Dermatology row above: it exists, but its doctor column is NULL. COUNT(*) counts rows, so Dermatology gets 1, which is wrong. COUNT(d.doc_id) counts non-NULL values, so Dermatology gets 0, which is right. In the dance analogy, COUNT(*) counts chairs and COUNT(d.doc_id) counts the people actually sitting in them.

Rule

After a LEFT JOIN, always count a column from the right-hand table: COUNT(d.doc_id), never COUNT(*).

Self join: a table shaking hands with itself

Think of your class photo and a photocopy of it. You compare every face in the photo with every face in the copy, then keep only the pairs where the first roll number is smaller than the second. "Pairs of doctors in the same department" needs DOCTOR twice, under two aliases, joined on the shared column. Cardiology has Meera (101) and Arjun (102), so the raw join produces four combinations:

d1d2Verdict
Meera (101)Meera (101)✗ paired with herself
Meera (101)Arjun (102)✓ keep
Arjun (102)Meera (101)✗ same pair, repeated
Arjun (102)Arjun (102)✗ paired with himself

One condition removes all three bad rows at once: AND d1.doc_id < d2.doc_id. Using <> removes only the self-pairs and leaves the duplicate.

NULL in one breath

NULL is the empty chair from the dance. You cannot ask "is this chair equal to 5?"; you can only ask "is this chair empty?" NULL means unknown, not zero. fee = NULL is never true; write fee IS NULL. SUM, AVG and COUNT(col) silently skip NULLs, so AVG(fee) over 900 and NULL is 900, while AVG(NVL(fee,0)) is 450. When the question says "treat NULL as 0", wrap the column in NVL(fee, 0) inside the aggregate.

NATURAL JOIN joins on every column that has the same name in both tables, automatically. It works in the lab because the tables were designed for it, but in an exam prefer JOIN … ON unless the question says NATURAL: it shows the examiner you know which arrow you are following.

5. Before you press Enter

  • Every table has an alias, and every column is prefixed with it (kills ORA-00918 ambiguous).
  • Every JOIN has an ON. A missing ON multiplies rows into a Cartesian product.
  • Aggregate + plain column in SELECT → every plain column is in GROUP BY (ORA-00937 / ORA-00979).
  • Condition on a total → HAVING, not WHERE (ORA-00934 group function not allowed here).
  • "Even if none" → LEFT JOIN and COUNT(right_table.column).
  • NULL handled: NVL(col,0) or IS NULL, never = NULL.
  • Text in single quotes with the exact case in the data ('CSE' ≠ 'cse'). Dates through TO_DATE('01-01-2021','DD-MM-YYYY').
  • Semicolon at the end. A PL/SQL block ends with / on its own line, after SET SERVEROUTPUT ON.

The 20-second viva answer

The rubric gives marks for "explains query logic confidently". Use this template, filling the blanks:

"The question asks for [what] per [group]. The subject table is [T1]. I join [T2] on [key] because [that fact] lives there. I used [INNER / LEFT] because rows [must / need not] appear without a match. WHERE filters rows, GROUP BY gives one row per [group], HAVING filters on the aggregate, and the aliases make the output readable."

Exam-day ritual, 60 seconds

Read the question twice. Underline nouns and signal words. Sketch the boxes and arrows. Ask the LEFT-or-INNER question. Say the expected row count. Write FROM first. Then type.

Question 1

Senior high-earners

INNER JOINWHERETO_DATEORDER BY

The hospital administrator wants to reward experienced senior staff. Display the doctor's name, department name and salary for every doctor who earns more than ₹80,000 and joined before 1 January 2021. Arrange the list from the highest salary to the lowest.

How to think
  1. Nouns: doctor (name, salary, join date) and department (name). Two tables. The arrow is DOCTOR.dept_id → DEPARTMENT.dept_id.
  2. Signal words: "who earns more than", "joined before" are about a single doctor's row → WHERE. "Arrange" → ORDER BY. No "each / per" → no GROUP BY, no aggregates.
  3. Join type: must a doctor appear even if the department is missing? No → INNER JOIN. Subject is DOCTOR.
  4. Skeleton: SELECT three columns / FROM doctor / JOIN department ON dept_id / WHERE two conditions joined by AND / ORDER BY salary DESC.
  5. Predict: six doctors; salary above 80,000 leaves four; joined before 2021 removes Dr. Arjun (2021). Expect 3 rows
Trap

Comparing a DATE column to a plain string depends on the session's date format and can throw ORA-01861. Always convert the string: TO_DATE('01-01-2021','DD-MM-YYYY').

Question 2

Recruitment planning

LEFT JOINCOUNTGROUP BY

The HR team is planning recruitment. For every department, show the department name and the number of doctors working in it. A department that currently has no doctors must still appear in the list, showing 0. Show the departments with the most doctors first.

How to think
  1. Nouns: department (name) and doctor (to count). Same arrow as Q1.
  2. Signal words: "for every department" → subject is DEPARTMENT and GROUP BY dept_name. "number of doctors" → COUNT. "must still appear, showing 0" → keep unmatched departments → LEFT JOIN with DEPARTMENT on the left.
  3. Join type: the question answered it for you: rows must appear without a match, so LEFT.
  4. Skeleton: SELECT dept_name, COUNT(...) / FROM department / LEFT JOIN doctor ON dept_id / GROUP BY dept_name / ORDER BY the count DESC.
  5. Predict: five departments in the table → Expect exactly 5 rows, one of them Dermatology with 0.
Trap

This is the COUNT trap from page 4. COUNT(*) will give Dermatology 1. Count a column from the doctor side: COUNT(d.doc_id).

Question 3

Doctor-wise revenue report

3-table JOINGROUP BYHAVINGNVLSUM · AVG · COUNT

The finance team needs a doctor-wise revenue report. For each doctor, show the doctor's name, department name, number of appointments, total fee collected and average fee. A cancelled appointment has a NULL fee: treat it as 0. Include only doctors who have handled at least 2 appointments. Arrange by total fee, highest first.

How to think

"For each doctor, show the doctor's name, department name, number of appointments, total fee collected and average fee. A cancelled appointment has a NULL fee: treat it as 0. Include only doctors who have handled at least 2 appointments. Arrange by total fee, highest first."

Two arrows, two ON clauses. DOCTOR sits in the middle, so the FROM starts there and each JOIN follows one arrow.

  1. Nouns: doctor, department, appointment → three tables, two arrows: DOCTOR.dept_id → DEPARTMENT and APPOINTMENT.doc_id → DOCTOR. DOCTOR is the hub in the middle.
  2. Signal words: "for each doctor" → GROUP BY doctor name (and department name, because it is in SELECT). "number of / total / average" → COUNT / SUM / AVG. "treat NULL as 0" → NVL(fee,0) inside SUM and AVG. "at least 2 appointments" is a condition on a COUNT → HAVING. "Arrange by total fee" → ORDER BY total_fee DESC using the alias.
  3. Join type: doctors with zero appointments are excluded anyway by "at least 2", so a plain INNER JOIN is correct.
  4. Skeleton: all seven lines of the skeleton. This is the "full report" shape.
  5. Predict: Meera 3, Arjun 2, Fatima 2, Rohan 2, Kavya 1, Sameer 0 → Expect 4 rows, Meera on top.
Trap

AVG(fee) skips the NULL and gives Dr. Arjun 900. AVG(NVL(fee,0)) gives 450. The question said "treat as 0", so 450 is the correct answer, and the examiner will ask you which one you chose and why.

Question 4

Patient outreach

LEFT JOINCOUNTIS NULLNOT IN

The outreach team wants to contact patients. (a) Show every patient's name, city and number of visits, including patients who have never visited. (b) Now show only the name and city of patients who have never taken an appointment.

How to think
  1. Nouns: patient and appointment. Arrow: APPOINTMENT.patient_id → PATIENT.patient_id. Subject is PATIENT.
  2. (a) Signal words: "every patient… including never visited" → LEFT JOIN from PATIENT. "number of visits" → COUNT(a.app_id), grouped by patient.
  3. (b) Signal word: "never". After the LEFT JOIN, the patients with no match are exactly the rows where the appointment side is NULL. So keep part (a)'s join and add WHERE a.app_id IS NULL. No GROUP BY needed.
  4. Alternative for (b): a subquery reads like English: patients whose id is NOT IN the list of patient ids in APPOINTMENT. Know both; the examiner may ask for "another way".
  5. Predict: six patients → (a) 6 rows; only Neha never visited → (b) 1 row.
Trap

Put a.app_id IS NULL in WHERE, not in ON. ON decides how rows match; WHERE filters the result. In the ON clause it would change the matching and return every patient.

Question 5

Peer-mentoring pairs

SELF JOIN3-table JOIN< trick

The hospital is starting a peer-mentoring programme in which each doctor is paired with a colleague from the same department. Display each pair (both doctors' names) along with the department name. A doctor must not be paired with themselves, and each pair must appear only once.

How to think
  1. Signal words: "pairs" + "same department" → comparing doctors with doctors → SELF JOIN: DOCTOR as d1 and DOCTOR as d2, joined on d1.dept_id = d2.dept_id.
  2. "not with themselves" and "only once": both handled by one condition, d1.doc_id < d2.doc_id (page 4). <> would leave the (Arjun, Meera) duplicate.
  3. "department name": a third arrow, d1.dept_id → DEPARTMENT.dept_id. Join DEPARTMENT once, through either alias.
  4. Join type: only real pairs are wanted → INNER JOIN everywhere.
  5. Predict: Cardiology has 2 doctors → 1 pair; Orthopedics 2 → 1 pair; Neurology and Pediatrics have one each → no pair. Expect 2 rows
Trap

Without aliases Oracle cannot tell the two copies apart and every column is "ambiguously defined". A self join is impossible without two different aliases.

Viva rapid-fire

Ten marks are for viva. One sentence each is enough; say it calmly.

Primary key vs foreign key?
A primary key uniquely identifies a row in its own table and cannot be NULL. A foreign key is a column that stores another table's primary key to link the two.
WHERE vs HAVING?
WHERE filters individual rows before grouping. HAVING filters groups after GROUP BY, so only HAVING can use COUNT, SUM or AVG.
INNER vs LEFT vs FULL OUTER JOIN?
INNER returns only matching pairs. LEFT keeps every row of the left table and pads missing matches with NULL. FULL keeps unmatched rows from both sides.
COUNT(*) vs COUNT(column)?
COUNT(*) counts rows. COUNT(column) counts non-NULL values in that column, which is why it gives 0 after a LEFT JOIN with no match.
DDL, DML, DCL, TCL?
DDL defines structure (CREATE, ALTER, DROP, TRUNCATE). DML changes data (INSERT, UPDATE, DELETE, SELECT). DCL controls access (GRANT, REVOKE). TCL controls transactions (COMMIT, ROLLBACK, SAVEPOINT).
What is a view?
A saved SELECT query that behaves like a virtual table. It stores no data of its own, so it always shows the current rows of the base tables.
NATURAL JOIN vs JOIN ON?
NATURAL JOIN automatically joins on all columns with the same name. JOIN ON lets you state the exact condition, which is safer when tables share unrelated column names.
What is NULL and how do you test for it?
NULL means the value is unknown or missing, not zero or empty. Test with IS NULL or IS NOT NULL; replace it with NVL(column, value).
1NF, 2NF, 3NF?
1NF: every cell holds one atomic value. 2NF: 1NF plus every non-key column depends on the whole primary key. 3NF: 2NF plus no non-key column depends on another non-key column.
COMMIT, ROLLBACK, SAVEPOINT?
COMMIT makes changes permanent. ROLLBACK undoes uncommitted changes. SAVEPOINT marks a point you can ROLLBACK TO without losing everything.
What is a cursor?
A PL/SQL pointer to a query's result set that lets you process rows one at a time: OPEN, FETCH in a loop, EXIT WHEN cursor%NOTFOUND, CLOSE.
What is a trigger? What are :NEW and :OLD?
A block that runs automatically BEFORE or AFTER an INSERT, UPDATE or DELETE. :NEW holds the incoming row values and :OLD the existing ones; RAISE_APPLICATION_ERROR stops the statement with a message.
DELETE vs TRUNCATE vs DROP?
DELETE removes rows and can be rolled back. TRUNCATE removes all rows quickly and cannot be rolled back. DROP removes the table itself.
